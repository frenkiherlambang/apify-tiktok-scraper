Playwright browser → inject session cookies → navigate to TikTok search UI → let TikTok's own JS fire the signed API call → intercept the response body via page.on('response') → normalize → push to Dataset. Scroll to paginate. Never touch the DOM for data.

1. Why not fetch the API directly

Worth stating up front so the design makes sense: /api/search/general/full/ requires X-Bogus / _signature / msToken params that are generated by TikTok's obfuscated webmssdk bundle and are bound to the exact query string. You can't just change offset=0 → offset=12 on a captured URL — the signature breaks and you get status_code: 10000 (captcha wall).

So the browser stays in the loop as a signing oracle. The efficiency win comes from blocking heavy resources, not from dropping the browser.

2. Endpoints to intercept

Don't limit to one. Register a matcher for several — same handler, different normalizers:

Endpoint	Use	Notes
/api/search/general/full/	Keyword search, mixed feed	Your spec. Mixes videos + user cards. Caps out ~300–450 items
/api/search/item/full/	Keyword search, "Videos" tab	Cleaner, deeper pagination. Recommend this as primary
/api/challenge/item_list/	Hashtag feed	Your sample data is tag-based (SamsungGalaxyS25Ultra). Searching #tag in general search is noticeably worse than the challenge endpoint
/api/post/item_list/	Profile feed	Cheap to add, high value
/api/comment/list/	Comments	Only if you need replies

Since your example JSON has a tag field at the root, I'd assume hashtag mode matters to you and would build both from day one.

3. Resource blocking (the actual efficiency lever)
js
await page.route('**/*', (route) => {
  const type = route.request().resourceType();
  // block: image, media, font  — NOT stylesheet
  if (['image', 'media', 'font'].includes(type)) return route.abort();
  return route.continue();
});

Gotcha: do not block stylesheet. TikTok's infinite scroll uses an IntersectionObserver on a sentinel element. With CSS stripped, layout collapses, the sentinel is permanently in-viewport, and pagination either fires in a runaway loop or stalls. Blocking image/media/font alone cuts bandwidth ~90%.

4. Capture handler
js
const buffer = [];
page.on('response', async (res) => {
  const url = res.url();
  if (!TARGETS.some(t => url.includes(t))) return;
  if (res.status() !== 200) return;
  try {
    const json = await res.json();
    if (json.status_code && json.status_code !== 0) {
      // 10000 = captcha/signature reject, 10101 = rate limited
      throw new CaptchaError(json.status_code);
    }
    buffer.push(json);
  } catch (e) { /* log, non-JSON or aborted */ }
});

Pagination loop: scroll → wait for a new response to land in buffer (or timeout) → repeat until has_more === 0, target count reached, or N consecutive empty scrolls. Carry search_id / cursor only for logging; TikTok's own JS manages it.

5. Cookie handling

Accept three formats and normalize internally: raw Cookie: header string, EditThisCookie/Playwright JSON array, and Netscape cookies.txt.

Cookies that actually matter: sessionid, sessionid_ss, sid_tt, sid_guard, ttwid, msToken, and critically tt-target-idc (e.g. alisg, useast2a). If the proxy exit region contradicts tt-target-idc, TikTok silently logs you out and you get anonymous results without any error.

Recommended flow:

Inject cookies into context.
Health check — hit /api/user/detail/ or read the SIGI state for isLoggedIn. Fail fast with a clear message rather than silently returning logged-out data.
Pin one Apify proxy session per cookie set (sessionId: hash(cookie)), residential, country matched to the cookie's IDC. Never rotate mid-run.
Persist refreshed cookies back to the KV store at the end — msToken rotates constantly and a stale one degrades results.

9. Build phases

Phase 1 (~2 days) — Playwright + cookie injection + health check + single-endpoint interception for one keyword, no pagination. Prove the payload shape.

Phase 2 (~2 days) — Scroll pagination, dedup by item.id, resource blocking, normalizer, Dataset output matching your schema.

Phase 3 (~2 days) — Hashtag + profile modes, cookie pool with round-robin and per-session proxy pinning, captcha detection with exponential backoff and session retirement.

Phase 4 (~1–2 days) — Comments, optional media download to KV store, INPUT_SCHEMA.json, README, cost tuning.

10. Known risks
Media URLs are signed and expire (~2h) and require the right Referer to fetch. If your consumer needs durable media, download during the run rather than storing hot links.
Search results are personalized. Logged-in scraping returns different results per account. That's a feature if you want realistic user-view data, a bug if you want reproducibility. Worth deciding explicitly.
Search depth caps around 300–450 items regardless of scrolling. To go deeper you need query fan-out (variants, sortBy=latest, date-window slicing).
Account risk — heavy scraping on a real sessionid can get the account rate-limited or banned. Use throwaway accounts, and cap concurrency at 1 request per session.
/api/search/general/full/ returns type: 1 (video) and type: 4 (user card) entries in the same array — the normalizer must branch, or you'll get null-heavy rows.
